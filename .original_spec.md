# Personal Markdown Notes for macOS

**Product + Technical Specification**  
**Version:** 0.1  
**Target:** macOS, Apple Silicon first  
**Implementation:** Rust + GPUI + selected Zed crates  
**Primary editor:** Zed `editor` + Zed `vim`  
**Storage:** Local Markdown files  
**Audience:** Single-user / personal-use application

---

# 1. Executive Summary

The application is a fast, local-first, keyboard-first Markdown note-taking application for macOS.

Its conceptual model is:

> A file browser, Markdown editor, Vim environment, search tool, and Markdown reader combined into one native-feeling desktop application.

The product should prioritize:

1. Instant access to local Markdown notes.
2. Extremely low keyboard latency.
3. Minimal UI friction.
4. Vim-quality modal editing.
5. Plain Markdown files as the source of truth.
6. Fast navigation across a large note directory.
7. Full-text search.
8. Command-driven interaction.
9. Clean Markdown preview.
10. No required account, cloud service, proprietary file format, or database.

The intended experience should feel closer to:

**Zed + Neovim + Obsidian file ownership**

than to:

**Apple Notes + rich-text editing**.

The application is intentionally not a general-purpose knowledge-management platform in v1.

The first version should avoid:

- cloud sync implementation
- collaboration
- proprietary document formats
- block-based editing
- databases as canonical storage
- plugins
- mobile applications
- AI functionality
- complex metadata systems
- WYSIWYG Markdown editing

The filesystem remains authoritative.

---

# 2. Product Vision

The product exists to make interacting with a directory of Markdown files feel as fast as interacting with source code in a high-performance editor.

A user should be able to:

```text
launch app
→ search for note
→ open note
→ edit with Vim motions
→ follow another file
→ preview Markdown
→ search whole vault
```

without reaching for the mouse.

The application should remain useful even if it disappears permanently tomorrow because every note remains a normal `.md` file.

---

# 3. Product Principles

## 3.1 Local files are the product

The canonical data model is:

```text
filesystem
    ↓
Markdown files
```

Not:

```text
database
    ↓
exported Markdown
```

Any database maintained by the application is disposable and rebuildable.

---

## 3.2 Keyboard first, not keyboard accessible

Keyboard interaction is not an alternative to mouse interaction.

It is the primary interface.

Every major action must be invocable through:

- a keyboard shortcut
- the command palette
- a Vim mapping where appropriate

GPUI is particularly suitable here because its interaction system treats actions, key contexts, and keybindings as first-class concepts.

---

## 3.3 Editing should feel like an editor, not a text area

The application should provide:

- low-latency cursor movement
- accurate selections
- smooth scrolling
- multi-cursor support where inherited from Zed
- syntax highlighting
- undo/redo
- Vim motions
- Vim operators
- text objects
- search
- registers
- macros
- repeat
- marks where supported

Zed's architecture already separates its core `Editor` from the Vim layer, with Vim acting as a relatively thin workflow layer over the editor.

---

## 3.4 Avoid unnecessary abstraction

Because this is a personal application:

- compatibility with arbitrary UI frameworks is unnecessary
- backwards compatibility is secondary
- GPL compatibility is irrelevant to architectural decisions
- using internal Zed crates is acceptable
- carrying some unused Zed infrastructure initially is acceptable

The goal is a useful application, not a reusable framework.

# 7. Primary Information Architecture

One workspace corresponds to one root filesystem directory.

Example:

```text
~/Notes/
│
├── inbox.md
├── todo.md
│
├── journal/
│   ├── 2026-08-20.md
│   ├── 2026-08-21.md
│   └── 2026-08-22.md
│
├── projects/
│   ├── notes-app.md
│   ├── homelab.md
│   └── travel.md
│
└── archive/
    └── ...
```

There is no required application-specific directory structure.

The app may create:

```text
.notes/
```

inside the root only if explicitly enabled.

Prefer storing internal application state under:

```text
~/Library/Application Support/<AppName>/
```

rather than polluting the notes directory.

# 17. Neovim Compatibility Strategy

Actual Neovim embedding is not part of v1.

This is deliberate.

## 17.1 v1

Use:

```text
Zed Editor
    +
Zed Vim
```

Advantages:

- single rendering model
- GPUI-native
- no RPC
- no terminal-grid emulation
- no duplicate buffer ownership
- simpler input methods
- simpler IME support
- simpler scrolling
- native selection rendering
- shared command system

---

## 17.2 Neovim interoperability

Provide:

```text
Note: Open in Neovim
```

Possible implementation:

```bash
nvim /absolute/path/note.md
```

or open in configured terminal.

When file changes externally, reload through filesystem watcher.

---

## 17.3 Optional future embedded Neovim backend

If exact Neovim behavior or plugins become important, add a research implementation.

Architecture:

```text
GPUI
  ↓
NvimBridge
  ↓ MessagePack-RPC
nvim --embed
```

Neovim officially exposes RPC and a UI protocol for external UI/embedder applications, including `nvim_ui_attach()`.

This should remain an experimental secondary editor backend.

Do not block the application on it.

# 33. External File Changes

The application must expect changes from:

- Neovim
- Git
- Finder
- shell commands
- sync services
- other Markdown applications

Use filesystem watching.

State machine:

```text
file event
   ↓
document dirty?
   ├── no → reload
   └── yes
        ↓
   compare disk content
        ↓
   conflict UI
```

# 34. Conflict Handling

If file changed externally and local editor contains unsaved modifications:

Show:

```text
File changed on disk.

[Keep My Changes]
[Reload from Disk]
[Compare]
```

Do not silently overwrite either version.

Autosave makes this rare but not impossible.

# 92. Upgrade Strategy for Zed

The application lives inside a Zed fork:

```text
origin = personal fork
upstream = zed-industries/zed
```

The fork is pinned to the revision it was created from.

There is **no routine upstream tracking**. Do not schedule periodic merges or rebases. A solo maintainer cannot keep pace with Zed's development velocity, and the application does not need new Zed features: the editor, Vim, fuzzy finder, and Markdown infrastructure are already mature at the pinned revision.

Policy:

1. Staying pinned indefinitely is an acceptable end state, not a failure mode.
2. Upgrading is a deliberate, rare event, motivated only by a concrete need such as a bug in a reused crate that upstream has fixed, or a specific capability the app genuinely requires.
3. When an upstream fix is needed, prefer cherry-picking the specific commit over a full merge.
4. A full merge of `upstream/main` should be treated as a project in its own right, undertaken only when the accumulated benefit clearly justifies the conflict-resolution cost.

Keep application-specific code mostly inside:

```text
crates/notes_app
crates/notes_*
```

not because upgrades are planned, but because the separation keeps any future upgrade or extraction tractable and keeps notes logic easy to find.

---

# 93. Upstream Patch Policy

Preferred order:

1. consume existing Zed capability
2. configure existing capability
3. wrap existing capability
4. add extension point upstream locally
5. modify generic crate directly

Because the fork is pinned rather than continuously merged (Section 92), directly editing generic Zed crates carries a low ongoing cost and is acceptable when wrapping would be awkward — for example, simplifying the project panel or stripping unwanted UI. The ordering above still applies because consuming and wrapping produce clearer code, not because merge conflicts must be avoided.

Maintain patches as small commits.

Example:

```text
zed-upstream
+
0001 notes-app binary
0002 notes actions
0003 simplified project panel
0004 Markdown-specific behavior
```

```text
command palette function
Vim function
```

Instead:

```text
NewNote action
```

invoked from four different surfaces.

This aligns with GPUI's action/keybinding model.

---

# 107. Architectural Rule: Avoid Neovim Synchronization

If embedded Neovim is eventually implemented, do not maintain:

```text
Zed Buffer ⇄ Neovim Buffer
```

for the same live editor.

Choose one authoritative editor backend per pane.

Either:

```text
ZedEditorBackend
```

or:

```text
NeovimEditorBackend
```

Never two simultaneously authoritative document models.

---

# 108. Architectural Rule: Keep Markdown Portable

Do not write invisible identifiers such as:

```markdown
<!-- notes-app-block-id: a81d... -->
```

unless a future feature absolutely requires them.

Prefer deriving relationships from:

```text
paths
headings
links
frontmatter
```

This maintains interoperability with Vim, Neovim, Obsidian, VS Code, GitHub, and CLI tools.

# 111. Most Important Implementation Decision

The first implementation milestone should **not** be:

> Build a note-taking app UI.

It should be:

> Determine the minimum set of Zed initialization and workspace components necessary to render one local Markdown document in Zed's Editor with Vim enabled inside a new GPUI application binary.

Once that works, the most technically risky requirement has been solved.

Everything afterward—explorer, palette, search, preview, settings, note creation—is mostly composition of existing systems.
